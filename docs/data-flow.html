How messy OSHA records become a sub’s verdict and a foreman’s answer

OSHA’s enforcement files have no company ID, so every fix happens in a named step. The build cleans, scopes and groups the records into a read-only warehouse. Matching ties those records to each subcontractor a GC enters, with the GC deciding anything red-flagged. The foreman’s chat answers only from the same named queries as the scorecard. Nothing is deleted along the way: bad values are flagged and broken rows are set aside with a reason.

The whole system, and where each part runs

Two halves meet at the warehouse. A build on Modal turns public files into a read-only DuckDB file and swaps it in only when its checks pass. The app reads that file, keeps every human and AI decision in Postgres, the one store a rebuild can’t touch, and calls the AI and web services only when their keys are set. Vercel serves the site and forwards /api to Modal, so the browser sees one site.

The build, step by step

One sub, from the form to its verdict

Adding a sub runs only the rules, so its card comes back in the same request. The page then sends a second request for every sub still resolving, four at a time. That request looks the company up if the GC asked, checks same-name matches in other states, matches the sub’s own name at addresses on its own website, and sends what is still uncertain to Jev or, when a record carries a red flag, to the GC. Later, the web check asks whose each leftover record is, when the GC presses its button or the project runs it by itself. Only one request works on a sub at a time, and anything the GC decides meanwhile stands.

One foreman question, from the phone to a checked answer

The foreman’s chat never queries the data itself. Its model picks from the named queries the scorecard runs and fills in their parameters, and code checks the answer before the foreman sees it. A sub with an open red-flag match question gets no answer about it until the GC has decided.

One name through the ten cleaning rules

The rules remove only noise that never tells two companies apart: case, punctuation, case-number prefixes and legal forms. Trade words, initials, numbers and place words stay, so 84 LUMBER is untouched and BRASFIELD CONSTRUCTION never becomes BRASFIELD & GORRIE.

Six rules the flow never breaks

Flag, don’t delete

Blank penalties stay blank instead of becoming $0, deleted citations are marked, and unmapped hazards go to “other”. Totals always reconcile, and the gate checks that they do.

Split rather than merge

A wrong split costs the GC a little review. A wrong merge can pin someone else’s fatality on a sub. So establishments merge only on identical keys, and companies are assembled per sub, where the GC’s evidence is.

The GC decides what a machine can’t

A record with a fatality, willful, repeat or failure-to-abate flag is never settled by the AI or the web, either way: it becomes a yes / no question, and the GC’s answer outlasts every AI run and re-match. The web settles a record by itself only for the sub’s own name at an address on its own site (M4), or when a project turns on auto-match.

Facts and decisions live apart

The warehouse is rebuilt from source every run. Match decisions sit in Postgres and point at deterministic establishment keys, so a rebuild never erases what a GC confirmed. When a cleaning change gives records new keys, scripts/rematch.py moves each decision with its inspections.

Answers come only from named queries

The foreman’s model picks from about a dozen tested queries and never writes SQL. The scorecard runs the same queries, so “fall protection” or “provisional” means the same thing in both views.

Nothing unchecked reaches the foreman

Every number, date and inspection ID in an answer must be in the tool results, or the answer is retried once and then rebuilt from the results. The coverage note is written by code, never by the model.
